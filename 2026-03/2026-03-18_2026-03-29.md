**Root cause analysis:**

- **OOM (18 workers):** Memory pressure occurs when cloning or installing dependencies for large monorepos. Mitigation: add a pre-clone repository size filter (e.g., skip repos with disk usage above 500MB) and increase per-worker memory allocation for remaining large repos.
- **Timeout (17 tasks, 16 in M2.7 upgrade):** Log analysis confirms recurring direct `github.com` fetch timeouts that are resolved by switching to `gh-proxy.com` ad hoc. This workaround is applied manually on a per-session basis. Mitigation: configure `gh-proxy.com` (or a similar proxy) as the default remote URL for all git operations, eliminating the need for per-session intervention.
- **Other (147):** These failures are expected given the candidate selection noise level. The primary remediation is upstream filtering improvement, not bot-side changes.

**Bot vs. task selection issues:**

- Bot-side problems: OOM and timeout are infrastructure and configuration issues that can be systematically addressed. The repeated proxy workaround in logs confirms timeout is a known, unresolved systemic issue.
- Task selection problems: The 76.1% incompatibility rate in new integration candidates is a task selection problem, not a bot execution problem. Tighter pre-queue filtering (e.g., requiring evidence of an LLM client abstraction layer or provider registry in the codebase) would improve the effective submit rate without requiring bot logic changes.

**Worker health summary:**

1362 normal completions, 18 OOM crashes, 164 timeout/error — giving a completion rate of approximately 87%. The 164 timeout/error workers represent the primary reliability gap.
